# CubeVision — カメラでルービックキューブの回転を追跡するアプリ

カメラ1つで、各ステッカーに色付き ArUco マーカーを貼った 3x3 ルービックキューブを映すと、**回した手順をリアルタイムに読み取り、
画面の3Dキューブで同じ動きを再現**します。スマートキューブ（Bluetooth 内蔵キューブ）がなくても、手順ログ・TPS・自動計測タイマー・
3Dリプレイが使えます。色を読まずにマーカーの ID でステッカーを判定するので、照明で色が変わっても取り違えません。

ブラウザだけで動く PWA です（インストール不要・処理はすべて端末内・映像は外部に送信しません）。
公開版: https://hsgwyuki0429-design.github.io/cube/ （main に入ると GitHub Pages に自動で反映）

## ステッカー

アプリが対応するステッカーは 1 種類だけです: **マスごとに違う 54 種類の符号のマーカーを、1 枚のステッカーに 2×2 で 4 個**（幅 1/2）並べたもの。
印刷用 PDF は `docs/stickers/cubevision_unique54_designs.pdf` の **5 ページ目「4 個・幅 1/2」**（16mm。`node scripts/aruco-stickers.mjs designs` で
作り直せます）。揃った状態の位置と向きのとおりに貼ります（貼り方は `cubevision_unique54_stickers.pdf` の 3 ページ目）。
1 枚の ID と向きから面の位置が分かるのでセンターが指で隠れても読め、4 個のどれかが見えていれば読めるので指に強い代わりに、ぶれ・遠さに弱くなります。

## できること

| 機能 | 内容 |
|---|---|
| 揃った状態から開始・6面スキャン | 揃ったキューブならスキャンなしで始められる。崩れたキューブは指示に従って1面ずつ見せると取り込む。指で隠れたマスは見えたときに埋まり、「物理的にありえるキューブのうち最も読みに合うもの」を選ぶ |
| リアルタイム追跡 | 回した手を検出して 3D キューブ（cubing.js）に反映。見えない面の回転は、後で影響が見えた時点で遡って推定 |
| 指に強い認識 | 読めなかったマスは切り出して読み直し、それでも読めなければ同じフレームのマーカーの色で補い、直前に同じマスで読めたステッカーを引き継ぐ。回している途中の層は別のまとまり（2×3 と 1×3）として面を組み立てる |
| 回転途中の形 | 層を回している途中のフレームから、どの層がどちら向きに何度回っているかを求め、手の手がかりにする（露光の短いスロー撮影の動画で効く） |
| 精密解析を最初から | 追跡を始めたときから録画を裏で重い設定で解き直し、追跡の手順と 3D に反映（画面上部に遅れを表示）。キューブが止まっている間に追いつく。フリーでも完成したら、完成を終わりとして前後から解き直して手順を直す |
| 手順の知識 | PLL・OLL・F2L・よく使う並びと、自分のソルブの手順を覚えていて、見分けにくい区間では手順として自然な読みを選ぶ（持ち方・左手の手順も同じに扱う） |
| 3D の傾き追従 | 3D キューブが、カメラに映っているキューブの角度（傾き・持ち替え）にそのまま追従。「自分から見た傾き」「固定」も選べる |
| 手順ログ | 持ち方基準（R U R' U' …）／センター色基準を切替。未確定の手・推定した手を区別して表示 |
| 解法ガイド | 今の状態から揃えるまでの手順を表示し、回すと自動で進む |
| タイマー | WCA スクランブルを生成し、今の状態から崩す手順を案内 → 崩し終わると自動でインスペクション → 最初の1手で開始 → 揃った瞬間に停止（スマートキューブと同じ流れ） |
| スロー動画の解析 | ブラウザのカメラは 60fps 前後まで。スマホのカメラアプリのスロー撮影（120・240fps）で撮った動画を読み込むと、全フレームを精密解析する。タイマーの「スロー動画から記録」は表示したスクランブルから解いた動画のタイムと手順を記録に足し、フリーの「動画を解析」は揃った状態から回した動画の手順を出す。スロー再生用に書き出された動画（30fps など）は撮影した fps を入れて実際の時間に直す |
| 手順の再構成・正確なタイム | 計測中の映像を端末内に一時録画し、全フレームを解析し直して、スクランブル後の状態と完成の両側から辻褄が合う手順を選び直す。タイムは「最初の手の回し始め」〜「最後の手の回し終わり」で、止めた瞬間は速報値、解析で確定 |
| 分析・履歴 | 手数・TPS・クロス/F2L/OLL/PLL の区間、ベスト・ao5・ao12。3D リプレイ、JSON/CSV 書き出し |
| ArUco の画面 | スロー撮影（240fps）の動画から手順を推定し、回転途中の形まで見られる（キューブモード）。シートを写してマーカーの検出率を測る（テストモード） |
| デモ | カメラがなくても、合成カメラ（three.js で描いたマーカー付きのキューブの映像）で全機能を試せる（`?demo`） |

## 使い方

```bash
npm install
npm run dev        # http://localhost:5173 を開く
```

スマホで使うときは同じ LAN で `npm run dev:lan` を実行し、表示された `https://<PCのIP>:5173/` をスマホで開きます
（カメラは HTTPS が必須なので自己署名証明書を使います。最初に出る警告は承認してください）。

1. **ステッカーを貼る** — 上の「ステッカー」の PDF（5 ページ目）を印刷して貼ります。
2. **カメラを置く** — キューブより少し上から、キューブの「カメラ側の面」と「上面」の **2面が映る** ようにすると精度が大きく上がります。
   マーカーは小さいので、近め（マスの間隔が画面の 65px 以上、1280 の映像で 35cm 程度まで）・明るい場所で。速く回すなら設定でフレームレートを 60fps に（既定）。
3. **始める** — 揃ったキューブなら「揃った状態から開始」。崩れたキューブは「6面スキャン」（画面の指示どおり、緑の面を正面・白を上など）。
4. **回す** — 3D キューブと手順ログに反映されます。
5. **タイマー** — 「タイマー」タブでスクランブルを出して計測。

詳しくはアプリ内の「使い方」を参照してください。

## しくみ

```
カメラ ──requestVideoFrameCallback（撮影時刻つき）──▶ 認識 Worker（OpenCV.js）
                                      ├ ArUco マーカーを検出（max(R,G,B) の明るさ・捨てられた四角の読み直し）
                                      ├ マーカーの ID と向きから見えている面を組み立てる（射影変換。1 列・1 枚の面も）
                                      ├ 読めなかったマス: 切り出して読み直し → 色で補う → 直前のフレームのステッカーを引き継ぐ
                                      ├ 回転途中の形: 回している層・角度（フレームをつないで向きと量）
                                      ├ 面の格子から連続的な姿勢（傾き）を推定（PnP）
                                      └ 追跡エンジン
                                          ├ 観測器: 一瞬（〜33ms）でも安定した読みを「観測」にする
                                          ├ デコーダ: 仮説 =（キューブ状態, 24通りの姿勢）のビームサーチ
                                          │  各観測で 0〜3 手＋持ち替えを展開し、予測される見え方（色・ステッカーの ID・
                                          │  回転途中の形）と照合
                                          └ 手の時刻: 回した層のセルが動き出した／止まったフレーム
メイン（Preact）◀── 手順・状態・姿勢 ──┘   → 3D 表示（cubing.js TwistyPlayer）・タイマー・履歴
   └ 追跡中は映像を WebCodecs で録画 → 別の Worker で全フレームを解析し直して、追跡を直す・タイムを確定
```

ポイントは **映像から手順を直接組み立てない** ことです。内部に持っているキューブ状態に候補の手を適用し、
「そうだとしたらカメラにはどう見えるか」を全候補で照合して、最も矛盾の少ない手順を選びます。
読めなかったマーカーや指で隠れたステッカーがあっても、他のステッカーとの整合性で正しい手が選ばれ、
カメラから見えない面の回転も、その影響が見える面に現れた時点で遡って推定されます。

**ArUco マーカー**: 各ステッカーのマーカーの ID が、揃った状態でのそのステッカーの位置（54 種類）を表します。色は ID から決まるので
照明に左右されず、どのステッカーがどこにあるかまで分かります（色は同じでも別のステッカーなら、その読みは矛盾として扱う）。
マーカーの向きから面の真ん中の位置が分かるので、センターが指で隠れても面を組み立てられます。

**指への対策**: ArUco は 4 隅と全部のビットが見えないと読めないので、指が少しかかったマーカーは読めません。組み立てた面の読めなかった
マスは切り出して拡大して読み直し、それでも読めなければ同じフレームで読めたマーカーの色を基準に色だけを補い（肌らしい色は不明のまま）、
直前のフレームで同じマスに読めていたステッカーを短い間だけ引き継ぎます。小さいマーカーを 4 個並べた配置にすると、半分隠れても
残りのマーカーで読めます。

**回転途中の形**: 層を回している途中のフレームでも、読めたマーカーをすべて「回っていないマス」か「回ったマス」で説明できる層と角度を
探します。形だけでは 90° ごとが区別できないので、フレームをつないで回し始めからの角度にし、回し終わった観測に「この層がこの向きに
90° 回った」という手がかりとして付けます。デコーダは、それと合わない手の並びのコストを上げます（手を決めつけない）。色だけでは
R と R' が見分けられない場面で効きます。露光中に層が大きく動くとマーカーが読めないので、主にスロー撮影の動画の解析で働きます。

**タイムの測り方**: 「観測」は回転の途中（約 45°）で起きるので、そのまま使うと開始は遅く、終了は早くなります。
フレームごとの記録から、回した層の側面のステッカーが静止状態から変わり始めたフレーム（開始）と、再び止まったフレーム（終了）を探し、
前後のフレームの中間を時刻とします。さらにソルブ後の解析では、面の格子で正規化した小さな画像を比べ、層の角が輪郭からはみ出し始める
10° 以下の動きまで拾います（キューブ全体の揺れは、回していないセルの差を引いて打ち消す）。カメラの時刻は表示時刻ではなく
撮影時刻（`captureTime`）を使います。

**精密解析（追跡の開始から）**: スマホではリアルタイムの認識が 1 秒 10〜20 枚程度しか処理できず、残りのフレームは捨てています。
追跡を始めたときから映像を端末内で圧縮して残し（WebCodecs。ハードウェアの H.264 を優先）、別の Worker に少しずつ渡して、
全フレームを重い設定で解き直します。途中結果が届くたびにリアルタイムの追跡をそれに乗り換え、その後の観測を通し直すので、
画面の手順と 3D も直ります。キューブが止まっているフレームは飛ばして追いつきます（動き出す直前と止まった直後の 1 枚は残すので、
時刻の正確さは変わりません）。完成したとき（タイマーでは止めたとき）は、完成状態を終わりとして前後から解き直します。直接見えなかった
端の手はリアルタイムの値を使い、それでも完成までたどれなければ「速報値」のまま残します（誤ったタイムを確定にしないため）。

**手順の知識**: PLL・OLL・F2L・よく使う並び（R U R' U' など）と、自分のソルブの手順を、持ち方（どの面を前にしたか）と左右反転に
よらない 3〜4 手の並びとして覚えています。直前の手に続く手が知っている並びでなければ、その読みのコストを少し上げます。

**3D の傾き**: 見つかった面の格子の各点（3D 座標は既知）と画像上の位置から、レーベンバーグ・マーカート法でカメラに対する回転を求め、
フレームごとの離散的な姿勢（中心の色で決まる）と掛け合わせて、3D キューブをカメラの映像と同じ向きに回します。

## 既製品の調査と採用したもの

「既存のものをできる限り使う」方針で GitHub を調査しました。

| プロジェクト | 内容 | このアプリでの扱い |
|---|---|---|
| [cubing.js](https://github.com/cubing/cubing.js)（MPL-2.0/GPL-3.0） | 3D キューブ表示・記法・状態計算・ソルバー・WCA スクランブル | **そのまま採用**（3D表示・解法・スクランブル・状態の検証） |
| [OpenCV.js](https://docs.opencv.org/)（4.10、ArUco に要るものだけを SIMD つきでビルド。`src/vendor/opencv/`, Apache-2.0） | 画像処理・ArUco | **採用**（ArUco マーカーの検出） |
| [AllefDouglasDev/rubik-cube](https://github.com/AllefDouglasDev/rubik-cube)（MIT） | ブラウザのキューブトレーナー。カメラで正面1面を見て手順を復号する実験機能 | **設計を参考**: ビームサーチ復号・ハンガリアン法の色割り当て。これを「最大3面」「24姿勢を仮説に含める（持ち替え対応）」「ソフトなコスト」「見失い検出と復帰」に拡張 |
| [kkoomen/qbr](https://github.com/kkoomen/qbr), [RubikVision](https://github.com/Charles-AM/RubikVison), [cube-cv](https://github.com/HANS-2002/cube-cv), [RubikClear](https://github.com/steelburn/RubikClear) | カメラで面を読むソルバー・タイマー（静止スキャン） | 手法を参考。いずれも手順の追跡はしない |

調査の結論として、**「面の色を読む」既製品は多数あるが、「回転を1手ずつリアルタイムに追跡する」既製品は実用レベルのものが見当たらない**
（上記 rubik-cube の実験機能が最も近い）ため、追跡部分はそれらを土台に作り込んでいます。以前は普通の色のステッカー（とステッカーレス）の
色を読んでいましたが、実物の照明・指・ステッカーレスで安定しなかったので、ArUco マーカー専用にしました。

## 精度の確認

カメラなしで同じ処理経路を検証できるようにしてあります（合成画像を Node の OpenCV.js で処理）。

- `npm test` — 状態モデル（CLAUDE.md の必須テスト）、cubing.js との整合、ソルバー、復号器のシミュレーション、
  合成画像からのマーカーの検出・面の組み立て（4 個の配置も）・再認識・色で補う・ID なし追跡・回転途中の形、
  ライブの追跡と精密解析（30fps・指が動いてマーカーを隠す）、前後両方向からの再構成
- `npm run build && npm run e2e` — ビルド済みアプリをヘッドレス Chromium で開き、デモモード（three.js の合成カメラ）で
  「6面スキャン → 30 手」を実行して、追跡結果を正解と比較。`E2E_MODE=timer` でタイマーの流れ
- `tests/debug/arucoEval.debug.test.ts` — 総合評価（1 フレームの認識・手順・速い回転を、マーカーの配置ごとに）

開発中の計測値（合成データ。実カメラでの値ではありません）:

| 条件 | 結果 |
|---|---|
| 1 フレーム、崩した状態・ランダムな向き・3 つの距離・指・ぶれ（60 場面・見えているマス 998）: 色が正しく分かったマス | 今の配置 72.1%（指なし 96.3%・指が半分まで 55.5%・半分以上 0%）／ 4 個・幅 1/2 62.2%（指なし 72.9%・半分まで 67.7%・半分以上 12.1%、遠い・ぶれが大きいと落ちる）。誤りはどちらも 0.3% 以下 |
| 30fps・2.5 手/秒・指が動いてマーカーを隠す・8 手 | 下の「マーカーの配置と回転途中の形」 |
| E2E 追跡（ヘッドレス Chromium・合成カメラ・30 手） | unique54・aruco12・aruco・4 個の配置とも正解（スキャン → 追跡） |
| 回転途中の形（R・U・F・L・D を 18°・31°・59° 回した途中） | 層と角度（90° ごとを除いて）が 5° 以内 |

## 制約

- マーカーは指が少しかかると読めません（読み直し・色で補う・直前の引き継ぎで補います）。4 個の配置は指に強い代わりに、ぶれと遠さに弱くなります。
- 30fps のカメラでは回している途中はぶれてマーカーが読めません。層が止まった瞬間に読めれば追えますが、速い回転はスロー撮影の動画の解析の方が確実です。
  どうしても説明できなくなると「見失い」を表示します（ごまかして誤った手順を記録しないため）。
- 精密解析は WebCodecs が使えるブラウザ（Chrome / Edge / Safari 16.4 以降など）が必要です。使えない場合はリアルタイムの結果がそのまま記録になります。
  解析中にページを閉じるとそのソルブは速報値のままです（録画は保存しません）。
- 3D の傾きは、カメラの焦点距離を一般的な画角から仮定して求めています（多少ずれても向きはほぼ合います）。
- 1面しか見えない置き方では、カメラの反対側の面の回転は後から推定になります。2面見える置き方を推奨します。
- 中層（M/E/S）回しは、センター基準のため両側の面を回したのと同じ手として記録されます。
- 3x3 専用です。

## 構成

```
src/cube/        キューブの状態モデル（3D座標モデル）、cubing.js との変換、ソルバー（専用 Worker）、区間分割、ステッカーの同一性（stickers.ts）
src/vision/      カメラ、認識 Worker、1 フレームの処理（pipeline.ts → arucoFrame.ts）、色、姿勢推定（pose.ts）、
                 録画（recorder.ts）、精密解析（refine.ts・fineTiming.ts・decode.ts・motion.ts・videoFile.ts）
src/aruco/       ArUco: 符号（codes.ts）・検出（detect.ts）・面の組み立て（cube.ts）・マーカーの配置（design.ts）・再認識（reread.ts）・
                 色で補う（colorFill.ts）・ID なし追跡（idTrack.ts）・回転途中の形（turn.ts）・代表色（palette.ts）と、ArUco の画面
src/track/       追跡エンジン（観測器・色モデル・ビームサーチ復号器・手順の知識・手の時刻）— カメラも DOM も知らない
src/scan/        6面スキャン（取り込み・状態の組み立て）
src/app/         アプリの状態（コントローラ・タイマー・設定・保存）
src/ui/          画面（Preact）
src/synthetic/   合成カメラ（three.js）とデモの台本
```
