# CubeVision — カメラでルービックキューブの回転を追跡するアプリ

カメラ1つで、手持ちの普通の 3x3 ルービックキューブを映すと、**回した手順をリアルタイムに読み取り、画面の3Dキューブで同じ動きを再現**します。
スマートキューブ（Bluetooth 内蔵キューブ）がなくても、手順ログ・TPS・自動計測タイマー・3Dリプレイが使えます。

ブラウザだけで動く PWA です（インストール不要・処理はすべて端末内・映像は外部に送信しません）。
公開版: https://hsgwyuki0429-design.github.io/cube/ （main に入ると GitHub Pages に自動で反映）

## できること

| 機能 | 内容 |
|---|---|
| 6面スキャン | 指示に従って1面ずつカメラに見せると、色と配置を自動で取り込み。完成でも崩れた状態でもOK。指で隠れたマスは見えたときに埋まり（読めていないマスは画面に点線）、艶の映り込みや白飛びにも強い。色は 1 枚ずつではなく「物理的にありえるキューブのうち最も読みに合うもの」として決めるので、白とクリーム色の黄のような紛らわしい色もピースの組み合わせで決まる。自信のないマスは点線で示し、タップで修正 |
| リアルタイム追跡 | 回した手を検出して 3D キューブ（cubing.js）に反映。見えない面の回転は、後で影響が見えた時点で遡って推定。**1 秒 10 手前後**の速い回転にも追従（60fps のカメラ推奨） |
| 精密解析を最初から | 追跡を始めたときから録画を裏で重い設定で解き直し、追跡の手順と 3D に反映（画面上部に遅れを表示）。キューブが止まっている間に追いつく。フリーでも完成したら、完成を終わりとして前後から解き直して手順を直す |
| 手順の知識 | PLL・OLL・F2L・よく使う並びと、自分のソルブの手順を覚えていて、見分けにくい区間では手順として自然な読みを選ぶ（持ち方・左手の手順も同じに扱う） |
| 3D の傾き追従 | 3D キューブが、カメラに映っているキューブの角度（傾き・持ち替え）にそのまま追従。「自分から見た傾き」「固定」も選べる |
| 手順ログ | 持ち方基準（R U R' U' …）／センター色基準を切替。未確定の手・推定した手を区別して表示 |
| 解法ガイド | 今の状態から揃えるまでの手順を表示し、回すと自動で進む |
| タイマー | WCA スクランブルを生成し、今の状態から崩す手順を案内 → 崩し終わると自動でインスペクション → 最初の1手で開始 → 揃った瞬間に停止（スマートキューブと同じ流れ） |
| 手順の再構成 | 録画をインスペクションから全フレーム解析し（止めたときには大半が済んでいる）、スクランブル後の状態と完成の両側から辻褄が合う手順を選び直す（途中が指で隠れていても、前後からつなぐ）。数十秒〜1 分ほどで、全手順・区間・3D リプレイを表示 |
| 正確なタイム | 計測中の映像を端末内に一時録画し、**全フレームを1枚ずつ解析し直して**タイムと手順を確定（数秒〜数十秒。止めた瞬間は速報値）。タイムは「最初の手の回し始め」〜「最後の手の回し終わり」で、誤差はフレーム間隔の半分程度（60fps なら ±8ms） |
| 分析・履歴 | 手数・TPS・クロス/F2L/OLL/PLL の区間、ベスト・ao5・ao12。3D リプレイ、JSON/CSV 書き出し |
| デモ | カメラがなくても、合成カメラ（three.js で描いたキューブの映像）で全機能を試せる |

## 使い方

```bash
npm install
npm run dev        # http://localhost:5173 を開く
```

スマホで使うときは同じ LAN で `npm run dev:lan` を実行し、表示された `https://<PCのIP>:5173/` をスマホで開きます
（カメラは HTTPS が必須なので自己署名証明書を使います。最初に出る警告は承認してください）。

1. **カメラを置く** — キューブより少し上から、キューブの「カメラ側の面」と「上面」の **2面が映る** ようにすると精度が大きく上がります。
   速く回すなら設定でフレームレートを 60fps に（既定）。実際の fps は画面上部に出ます。
2. **6面スキャン** — 画面の指示どおり（標準配色なら「緑の面を正面・白を上」など）に面を見せます。少し止めると自動で取り込みます。
3. **回す** — 3D キューブと手順ログに反映されます。最初は1手ずつ軽く止めるくらいから。
4. **タイマー** — 「タイマー」タブでスクランブルを出して計測。

詳しくはアプリ内の「使い方」を参照してください。

## しくみ

```
カメラ ──requestVideoFrameCallback（撮影時刻つき）──▶ 認識 Worker（OpenCV.js）
                                      ├ ステッカーらしい四角形を検出（輝度 + a*/b* のエッジ）
                                      ├ 形と間隔が揃う四角形を 3x3 格子に当てはめ（射影変換）  ← 最大3面
                                      ├ 面をカメラフレーム（正面/上/右…）と向きに割り当て
                                      ├ 各セル中央部の色を CIELab でサンプリング（手の部分は MediaPipe で除外）
                                      ├ 面の格子から連続的な姿勢（傾き）を推定（PnP）
                                      └ 追跡エンジン
                                          ├ 観測器: 一瞬（〜33ms）でも安定した読みを「観測」にする
                                          ├ デコーダ: 仮説 =（キューブ状態, 24通りの姿勢）のビームサーチ
                                          │  各観測で 0〜3 手＋持ち替えを展開し、予測される見え方と照合
                                          └ 手の時刻: 回した層のセルが動き出した／止まったフレーム
メイン（Preact）◀── 手順・状態・姿勢 ──┘   → 3D 表示（cubing.js TwistyPlayer）・タイマー・履歴
   └ タイマー計測中は映像を WebCodecs で録画 → 止めた後、別の Worker で全フレームを解析し直して確定
```

ポイントは **映像から手順を直接組み立てない** ことです。内部に持っているキューブ状態に候補の手を適用し、
「そうだとしたらカメラにはどう見えるか」を全候補で照合して、最も矛盾の少ない手順を選びます。
色の読み間違いや指で隠れたステッカーがあっても、他のステッカーとの整合性で正しい手が選ばれ、
カメラから見えない面の回転も、その影響が見える面に現れた時点で遡って推定されます。

**速い回転への対応**: 10 手/秒では 1 手が 0.1 秒、層がそろって見える時間は 1〜2 フレームしかありません。観測器はその一瞬を拾い、
デコーダは観測の間に最大 3 手（見失いからの復帰は 4〜5 手）を、コストの下限で枝刈りしながら探します。回転途中で格子に合わない
セルは軽く扱い、指（手の検出）で隠れたセルは使いません。

**タイムの測り方**: 「観測」は回転の途中（約 45°）で起きるので、そのまま使うと開始は遅く、終了は早くなります。
フレームごとの記録から、回した層の側面のステッカーが静止状態から変わり始めたフレーム（開始）と、再び止まったフレーム（終了）を探し、
前後のフレームの中間を時刻とします。さらにソルブ後の解析では、面の格子で正規化した小さな画像を比べ、層の角が輪郭からはみ出し始める
10° 以下の動きまで拾います（キューブ全体の揺れは、回していないセルの差を引いて打ち消す）。カメラの時刻は表示時刻ではなく
撮影時刻（`captureTime`）を使います。

**精密解析（追跡の開始から）**: スマホではリアルタイムの認識が 1 秒 10〜20 枚程度しか処理できず、残りのフレームは捨てています。
追跡を始めたときから映像を端末内で圧縮して残し（WebCodecs。ハードウェアの H.264 を優先）、別の Worker に少しずつ渡して、
全フレームを仮説を倍に増やした重い設定で解き直します。途中結果が届くたびにリアルタイムの追跡をそれに乗り換え、その後の観測を
通し直すので、画面の手順と 3D も直ります。1 フレームに 0.2〜1 秒かかるので、キューブが止まっているフレームは飛ばして追いつきます
（動き出す直前と止まった直後の 1 枚は残すので、時刻の正確さは変わりません）。完成したとき（タイマーでは止めたとき）は、完成状態を
終わりとして前後から解き直します。直接見えなかった端の手はリアルタイムの値を使い、それでも完成までたどれなければ「速報値」の
まま残します（誤ったタイムを確定にしないため）。

**手順の知識**: PLL・OLL・F2L・よく使う並び（R U R' U' など）と、自分のソルブの手順を、持ち方（どの面を前にしたか）と左右反転に
よらない 3〜4 手の並びとして覚えています。直前の手に続く手が知っている並びでなければ、その読みのコストを少し上げます。正面しか
見えない区間でも、手順として自然な読みを選びやすくなり、手順の途中に雑音の手を挟む読みが不利になります。

**3D の傾き**: 見つかった面の格子の各点（3D 座標は既知）と画像上の位置から、レーベンバーグ・マーカート法でカメラに対する回転を求め、
フレームごとの離散的な姿勢（中心の色で決まる）と掛け合わせて、3D キューブをカメラの映像と同じ向きに回します。

色の判定は汎用の色分類ではなく、**スキャン時にそのキューブ・その照明で6色を実測**して使います（各色9枚ずつになるよう
ハンガリアン法で割り当て）。パステルなど変わった配色にも対応し、追跡中も確信の持てる観測で代表色をゆっくり補正します。

調査の結論として、**「面の色を読む」既製品は多数あるが、「回転を1手ずつリアルタイムに追跡する」既製品は実用レベルのものが見当たらない**
（上記 rubik-cube の実験機能が最も近い）ため、追跡部分はそれらを土台に作り込んでいます。

## 精度の確認

カメラなしで同じ処理経路を検証できるようにしてあります。合成画像だけでは実物の難しさが分からないので、
**実写**と**実物らしい合成映像**の両方で試します。

- `npm test` — 状態モデル（CLAUDE.md の必須テスト）、cubing.js との整合、ソルバー、復号器のシミュレーション、
  OpenCV.js による合成画像からの面検出、合成フレーム → 追跡の通し試験、6面スキャン、区間分割、
  **実写の 6 面からのスキャン**（`tests/real.test.ts`）、**実物らしい条件でのスキャン**（艶の映り込み・白飛び・持つ指・
  手の検出の失敗・チェックの背景）、前後両方向からの再構成（途中が隠れた場合）
- `npm run build && npm run e2e` — ビルド済みアプリをヘッドレス Chromium で開き、デモモード（three.js の合成カメラ、
  回転中は指が一部を隠す）で「6面スキャン → 30 手」を実行して、追跡結果を正解と比較。`E2E_MODE=timer` でタイマーの流れ
- `tests/speed.ts` — 高速回転のシミュレーション（回転途中の層・モーションブラー・指の遮蔽・手の揺れ・正確なタイムスタンプの 30/60fps）。
  `scene` で実物らしい条件（`tests/realism.ts`）も加えられる

実写での確認に使った写真・動画: [dwalton76/rubiks-cube-tracker](https://github.com/dwalton76/rubiks-cube-tracker) の
テスト写真（MIT、`tests/fixtures/real/` に同梱）と、[exactful/rubiks-cube-face-detection](https://github.com/exactful/rubiks-cube-face-detection)
のデモ動画（手持ち・背景にチェックのシャツ。ライセンス表記がないため同梱はしていない）。これで見つかった問題:
実物のステッカーは角が丸く、従来の多角形近似ではほとんど検出できていなかった／中央が白飛びして黄と白が同じ値になる／
チェックのシャツが面に見える。いずれも直してテストにした。

## 制約

- 10 手/秒前後まで追えるのは、カメラが 60fps（少なくとも 30fps）で、面がはっきり映っているときです。暗い場所ではシャッターが遅くなり
  ブラーが増えます。どうしても説明できなくなると「見失い」を表示します（ごまかして誤った手順を記録しないため）。
- 精密解析は WebCodecs が使えるブラウザ（Chrome / Edge / Safari 16.4 以降など）が必要です。使えない場合はリアルタイムの結果がそのまま記録になります。
  解析中にページを閉じるとそのソルブは速報値のままです（録画は保存しません）。
- 3D の傾きは、カメラの焦点距離を一般的な画角から仮定して求めています（多少ずれても向きはほぼ合います）。
- 1面しか見えない置き方では、カメラの反対側の面の回転は後から推定になります。2面見える置き方を推奨します。
- 溝がほとんど見えないステッカーレスキューブで、同じ色が大きくつながった状態（完成間際など）は検出が不安定になることがあります。
- 中層（M/E/S）回しは、センター基準のため両側の面を回したのと同じ手として記録されます。
- 3x3 専用です。

## 構成

```
src/cube/        キューブの状態モデル（3D座標モデル）、cubing.js との変換、ソルバー（専用 Worker）、区間分割
src/vision/      カメラ、認識 Worker、四角形検出（OpenCV.js）、格子当てはめ、面の配置、色、手の検出（MediaPipe）、
                 姿勢推定（pose.ts）、録画（recorder.ts）、精密解析（refine.ts・fineTiming.ts・decode.ts・motion.ts）
src/track/       追跡エンジン（観測器・色モデル・ビームサーチ復号器・手順の知識・手の時刻）— カメラも DOM も知らない
src/scan/        6面スキャン（取り込み・色割り当て・自動補正）
src/app/         アプリの状態（コントローラ・タイマー・設定・保存）
src/ui/          画面（Preact）
src/synthetic/   合成カメラ（three.js）とデモの台本
src/aruco/       色付き ArUco ステッカーの検証ページ（aruco.html。240fps の録画から手順の推定・検出率。docs/aruco-phase0.md）
tests/           Vitest（tests/render.ts はテスト用のソフトウェアレンダラ、tests/speed.ts は高速回転のシミュレーション）
scripts/e2e.mjs  ヘッドレス Chromium による E2E
```
