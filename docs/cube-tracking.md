# Phase 0.5 — キューブ姿勢追跡

一度キューブを指定したら、その後はスマホやキューブが多少動いても
3x3 グリッドが面に貼り付いたまま追従する仕組み。

Phase 0（`docs/phase0-findings.md`）の色分類・Move Tracker はそのまま。
このレイヤが差し替えるのは **ROI の座標の供給元だけ** で、下流は一切変えていない。

```
Camera
  ↓
Cube pose tracking      ← Phase 0.5（このドキュメント）
  ↓  面の四角形
Homography → 3x3 セル座標
  ↓
Color classification    ← Phase 0 のまま
  ↓
Move Tracker            ← Phase 0 のまま
```

---

## 1. 採用アルゴリズムと、その理由

### 全体方針

**毎フレーム全画面から再検出しない。**
「前フレームのモデルを動かして、観測と整合するか確かめる」方向で解く。
これは Phase 0 の Move Tracker（候補手を状態機械に適用して見え方を照合する）と
同じ考え方で、`CLAUDE.md` のアーキテクチャ原則 §2 に沿っている。

```
初期化（半自動）
  ↓
毎フレーム:
  1. 前フレームのモデルから特徴点を張り直す
  2. ピラミッド型 Lucas-Kanade で追跡
  3. 面ごとに RANSAC でホモグラフィを再推定
  4. 幾何の妥当性を検証（凸性 / 面積 / 巻き方向 / ジャンプ / 3面の面積比）
  5. グリッドロック比で「本当にキューブか」を確かめる
  6. 使えない面は剛体構造から再構成
  7. 共有頂点を一致させる
  8. 信頼度を更新 → TRACKING / DEGRADED / LOST
```

### なぜ OpenCV.js を使わなかったか

必要なのは実質 **Lucas-Kanade とホモグラフィ推定の2つだけ**で、
どちらも数百行の自前実装で足りる。実際に必要になった要素は:

| 必要なもの | 実装 | 行数の目安 |
|---|---|---|
| ピラミッド型 LK | `src/tracking/opticalFlow.ts` | 約 230 |
| N点対応 → ホモグラフィ（正規化DLT） | `src/tracking/geometry.ts` | 約 120 |
| RANSAC | 同上 | 約 60 |
| 四角形の妥当性判定 | 同上 | 約 90 |

これに対し OpenCV.js は wasm が数MB あり、PWA の初回ロードを大きく圧迫する
（企画書 §9 が挙げているリスクそのもの）。**追跡を足しても Worker バンドルは
1.9KB → 27KB にしか増えていない。**

副次的な利点として、自前実装は Node でそのままユニットテストできる。
合成映像を流し込んで px 単位で評価するハーネス（§7）は、
wasm 依存だと同じようには組めなかった。

**OpenCV.js を検討すべきになる条件**: ROI の完全自動検出（輪郭抽出・
Hough 変換）が必要になったとき、または LK の性能が実機で足りないと分かったとき。

### 特徴点をどこに置くか

**ステッカーの中央には置けない。** 単色でテクスチャが無く、LK が解けない。
実測では、セル中央27点のうち追跡できたのは8点だけだった
（`tests/opticalFlow.test.ts` に固定してある）。

置くのは **黒い枠線の交点・T字部・面の角** — `(u,v) ∈ {inset, 1/3, 2/3, 1-inset}`
の 4x4 格子、1面16点。ここは2方向に勾配があるので開口問題が出ない。

**外周は面の縁ちょうどではなく、少し内側に寄せる（既定 7%）。**
縁に置くと LK の窓に背景と隣接面（別の平面）が混入し、系統的なドリフトになる。
実測で平均セル誤差が **39px → 1.1px** まで変わった。これが Phase 0.5 で
最も効いた1行。

## 2. 初期化（半自動 + 段階的フォールバック）

完全自動検出はやっていない。「初回だけ人間が補助してよい。以後は操作不要」を優先した。

| Level | 操作 | 精度 | 備考 |
|---|---|---|---|
| 1 | キューブを1回タップ | 誤差が大きく、失敗しうる | 種モデルを置いてエッジ吸着。合成映像では成功したりしなかったり |
| 2 | 手前の角 + 3方向の隣接頂点を指定（4タップ） | 初期誤差 約7px | アフィン近似 + エッジ吸着 |
| 3 | 手動 ROI 3枚を合わせて「現在の ROI から初期化」 | **誤差 0** | 最も確実。Phase 0 の UI をそのまま使う |

Level 3 は Phase 0 の手動 ROI をそのまま初期モデルにするので、
**ユーザーは既に知っている操作だけで自動追跡に入れる。**
ブラウザ実機検証でも、この経路は初期化直後に
`conf 1.00 / 再投影誤差 0.01px / 48点中48点` で入る。

### 六角形モデル（Level 1, 2 の内部表現）

立方体を角から見ると可視頂点は7個で、3面はそれぞれ辺を共有する。
手前の頂点 N と、そこから伸びる3本の辺ベクトル p, q, r（計8自由度）で表す。

```
        N+p+r
      /       \
  N+p    U     N+r
   |  \     /  |
   |    N      |
F  |   /   \   |  R
  N+p+q     N+q+r
      \  N+q  /
```

- `U = {N+p, N, N+r, N+p+r}`
- `F = {N+p, N, N+q, N+p+q}`
- `R = {N+r, N, N+q, N+q+r}`

**これはアフィン近似で、透視による「対辺が平行でない」ぶんを表現できない。**
強い透視では系統誤差が残る（実測で最大 40px 弱）。エッジ吸着で 7px 程度まで
落ちるが、正確さが要る場面では Level 3 を使うこと。
追跡が始まれば面ごとの射影変換になるので、この制約は初期化にしか効かない。

エッジ吸着は8自由度の座標降下で、9本の辺（内側3本 + 外形6本）に沿った
輝度勾配の合計を最大化する。同じ関数を局所再検出にも使っている。

## 3. 追跡状態

```
UNINITIALIZED → INITIALIZING → TRACKING ⇄ DEGRADED → LOST
                                              ↑          │
                                              └──────────┘
                                          （再初期化が必要）
```

| 状態 | 意味 | 下流への影響 |
|---|---|---|
| `UNINITIALIZED` | まだ指定されていない | 色を読まない |
| `INITIALIZING` | 初期化直後の確認中（既定2フレーム） | 色を読まない |
| `TRACKING` | 直接観測できた面が2枚以上あり、信頼度も十分 | 通常動作 |
| `DEGRADED` | 一部を見失っている。モデルは保持 | 見失った面だけ色を読まない |
| `LOST` | 追跡不能 | **Move Tracker も停止**し、再取得を要求 |

**直接観測できた面が2枚あれば TRACKING でよい。**
立方体は剛体で、ある面の4隅のうち3隅は他の2面と共有しているため、
残る1面は誤差を溜めずに再構成できる（§5）。

## 4. 信頼度とグリッドロック比

### 面ごとの信頼度

```
confidence = (インライア率 × 0.55 + 誤差スコア × 0.45) × ロック係数
  誤差スコア = max(0, 1 - 再投影誤差 / RANSAC閾値)
  ロック係数 = clamp((ロック比 - minGridLock) / (fullGridLock - minGridLock), 0, 1)
  インライアが minInliersPerFace 未満なら 0
```

全体の信頼度は3面の平均。

### グリッドロック比（別物体への貼り付き検出）

**これが Phase 0.5 で二番目に重要な仕組み。**

特徴点の整合だけを見ていると、**背景の格子模様に一様に貼り付いたまま
高い信頼度を出し続ける**。実際、初期の実装ではキューブを画面外へ飛ばしても
LOST にならず、背景のテクスチャを追い続けていた。

ロック比 = 正しい位置での稜線強度 / 半セルずらした位置での稜線強度（4方向平均）

- 本物の 3x3 グリッド上なら、正しい位置は黒線に乗り、ずらすとステッカー中央に落ちる → 比が大きい
- 背景の一様なテクスチャならどちらも同じくらい → 比は 1 付近

**比なので拡大縮小・照明・コントラストに影響されない。**
支持度の絶対値を基準値と比べる方式も試したが、拡大縮小で誤検出した。

検出器の形も重要で、**黒いグリッド線は段差エッジではなく「暗い稜線」**。
`|I(+n) - I(-n)|` では線の中心で 0 になってしまうので、
両側の明るさの平均から中心を引く稜線検出器を使う。

合成データでの実測値:

| 状況 | ロック比 |
|---|---|
| 正常追跡 | 1.84 〜 2.24 |
| 部分遮蔽でずれた面 | 1.3 〜 1.6 |
| 遮蔽・キューブ消失 | 0.0 〜 1.0 |

既定は `minGridLock = 1.5` / `fullGridLock = 1.8`。
この値でどのシナリオでも誤追跡 0% になる。

> **注意**: これは合成データでの較正値。実キューブのステッカー間隔・
> コントラスト・照明で変わる。設定パネルから実行時に変更できるようにしてあるので、
> 実機で測って決め直すこと。

### 面ごとに評価すること

ロック比を3面平均で判定すると、**1面が手で隠れただけで正常な面まで
巻き添えで LOST になる**。必ず面ごとに評価する。

## 5. 見失った面の扱い

観測できなかった面は、**キューブの剛体構造から再構成する。**

使える面が2枚あれば六角形モデルの4パラメータ全てが決まる。
1枚しか無くても3つは決まるので、残る1本は「決まった2本が前フレームから
どう変わったか」から 2x2 の線形変換を解いて前フレームの値に当てる
（既知2ベクトルが平行に近いときは悪条件なので予測しない）。

以前は「成功した面のインライアから全体ホモグラフィを推定して引きずる」方式だったが、
誤差が蓄積して遮蔽が明けても戻らなくなった（実測で11px ずれたまま追跡継続）。
剛体構造を使うほうが正確で、実装も小さい。

見失った面をその場に**凍結**するのも駄目で、遮蔽が明けたときにモデルが
実物から離れすぎていて LK が戻れなくなる（実測で17px ずれたまま復帰不能）。

さらに、共有頂点の平均に**観測できていない面を入れてはいけない**。
正しく追えている面の頂点まで引っ張られる（U面が最大15px ずれた）。

### 予測面のグリッド吸着

予測で置いた面は、面内 (u,v) を少しだけ動かしてグリッドに一番よく乗る位置を探す。
**探索範囲は必ず半セル未満に制限する。** それ以上動かせるようにすると
1セル隣にも同じくらい乗ってしまい、セル単位でずれたまま高いスコアを出す。

吸着は幾何の補正であって観測の証拠ではないので、**吸着しただけの面を
「可視」と主張してはいけない。** ここを間違えると誤追跡率が 20% 出る。

## 6. LOST の条件と復帰

| 条件 | 既定値 | 挙動 |
|---|---|---|
| 直接観測できた面が2枚未満 | — | DEGRADED |
| DEGRADED が続く | 45フレーム | LOST |
| **全ての面を見失った状態が続く** | 8フレーム | **即 LOST** |
| DEGRADED から復帰 | 良好が3フレーム連続 | TRACKING |

全面を見失った後に盲目的な再ロックを許すと、**1セルずれた位置に貼り付いたまま
高い信頼度を出し続ける**（実測で33px ずれたまま TRACKING を継続）。
グリッドは1セル周期なので、内側の線だけでは区別できない。

なので **全面消失は短時間で LOST にして再取得を要求する。**
誤った ROI で色を読み続けて Move Tracker の状態を壊すより、正直に失敗する方がよい
（`CLAUDE.md` 原則 §3）。

一部の面だけの遮蔽なら、残りの面と剛体構造でモデルが保てるので復帰できる。

### 局所再検出

完全に LOST にする前に、予測位置の周りでエッジに貼り直す。
全画面スキャンはしない。**「本当に全面を観測できていない」ときだけ**動かす —
信頼度が下がっただけでモデルを動かすと、正しく追えているものを壊す（実測で確認）。

## 7. 幾何の破綻ガード

個々の四角形の検証（凸性・面積・巻き方向・頂点ジャンプ・アスペクト）に加えて、
**モデル全体が立方体としてありえるか**を毎フレーム見る。

立方体を角から見た3面の面積は同程度になるので、
最大/最小が 6 倍を超えたらモデル破綻とみなして全面を無効にする。

個々の四角形の検証だけでは、毎フレーム少しずつ膨らむ破綻を止められない。
1フレームの面積変化の上限も 1.8 → 1.35 に締めた（1.8 は毎フレーム倍増を許す）。

## 8. セルのサンプリング

面の四角形 → ホモグラフィ → 各セルの中央 `cellSampleInset`（既定 0.5 = 中央50%）の
領域を `samplesPerAxis²` 点サンプリングして平均。
**手動 ROI と全く同じ計算**なので、色分類より下流は追跡モードでも一切変わらない。

`rotate` / `mirror` も手動 ROI と同じ意味で効く。

見失った面は `trusted: false` を返し、色分類も Move Tracker も使わない。

## 9. 性能

### Node（合成シナリオ、480x360）

追跡 1フレームあたり **6.4 〜 8.1ms**（内訳はオプティカルフローが大半）。

### ブラウザ（Chromium ヘッドレス、ソフトウェアレンダリング、480x360）

| 項目 | 実測 |
|---|---|
| tracking ms | 6.4 〜 10.3 |
| sampling ms | 0.06 〜 0.09 |
| capture ms（createImageBitmap） | 1.2 〜 5.9 |
| worker ms 合計 | 9.2 〜 14.4 |
| 処理 fps | 15 〜 28 |

> ヘッドレスのソフトウェアレンダリングでの値であって実機の値ではない。
> Phase 0 の時点でも同じ環境でレイテンシが 18ms 出ていた（`docs/phase0-findings.md` §5）。

### Worker に置いた理由（実測に基づく判断）

追跡は Worker 側に置いた。メインスレッドに置くと
**同じフレームをもう一度フル解像度で読み戻す必要があり、二重コストになる**
（Worker は色サンプリングのために既に `getImageData` 済みのピクセルを持っている）。
「メインスレッド版と worker 版を比較する」以前に、メインスレッド版は
readback がもう1回増えるぶん確実に不利になるため、比較する意味が無い。

UI 描画は追跡とは独立した rAF ループで回しているので、
追跡が重くなっても描画は止まらない。

## 11. ブラウザ実機経路の検証

Chromium の `--use-file-for-fake-video-capture` に合成キューブ動画（Y4M）を
流し込み、`getUserMedia → rVFC → createImageBitmap → Worker → 追跡 → 色分類`
の全経路を通した。

```bash
VIDEO_OUT=/tmp/cube.y4m npm run video
# Chromium を --use-file-for-fake-video-capture=/tmp/cube.y4m で起動
```

**この経路でしか出なかった不具合が2つあった**（どちらも修正済み）:

1. Worker でグレースケールバッファを使い回していたため、`buildPyramid` が
   レベル0を**参照で**保持し、前フレームのピラミッドの中身が今フレームで
   上書きされていた。オプティカルフローが同一画像同士を比較する状態で、
   動きが始まった瞬間に壊れていた。Node のテストは毎フレーム新規確保していたため
   露見しなかった。→ ダブルバッファで解決。
2. Worker が返す追跡座標がピクセル単位のままで、ROI・オーバーレイ・録画が
   期待する正規化座標と食い違っていた。→ Worker 内で正規化して返す。

### 分かったこと: 追跡品質は「処理できた fps」で決まる

| 動画 | 処理 fps | 結果 |
|---|---|---|
| 15fps | 15（フレーム落ちなし） | **6秒以上 TRACKING を維持**、再投影誤差 0.01〜0.42px、信頼度 0.65〜1.00 |
| 30fps | 28（フレームを落とす） | 数秒で DEGRADED / LOST |

同じ動きでも、フレームを落とすと**1フレームあたりの変位が倍増**して追跡が破綻する。
カメラが 60fps 出ていても処理が 30fps しか出なければ、実質 30fps 相当の
難しさになる。**実機では「処理できた fps」を見ること。**

## 12. 既知の制約

- **完全自動のキューブ検出はできていない。** タップ1回からの初期化は
  成功しないことがある。確実なのは手動 ROI からの初期化（Level 3）。
- **大きな姿勢変化には追従しない。** キューブ全体を大きく回して別の物理面が
  正面に来る場合は対象外（Phase 0.5 のスコープ外）。DEGRADED → LOST → 再初期化になる。
- **全面遮蔽 + 移動からの自動復帰はしない。** 1セルずれた位置に貼り付く危険が
  あるため、意図的に LOST にして再取得を要求している。
- **面ラベル（U/F/R）は幾何的な位置**（上 / 前 / 右）であって、空間面への
  割り当てはユーザー設定。追跡中に入れ替わることはない。
- **閾値は全て合成データでの較正値。** 実キューブでは変わる。
- 合成レンダラのステッカーは完全な平面・一様色で、実物の反射・影・
  丸角・ロゴは再現していない。実機の値は必ず別に測ること。

## 13. 実機で次に測る項目

1. **処理できた fps**（カメラの fps ではなく）。ここが追跡品質を決める。
2. `tracking ms` の実測。16ms/フレームの予算にどれだけ食い込むか。
3. グリッドロック比の分布。実キューブのステッカー間隔とコントラストで
   `minGridLock` / `fullGridLock` を較正し直す。
4. タップ1回からの初期化の成功率。低ければ Level 3 を既定の導線にする。

   （セル座標が動くぶんサンプリングがぶれる可能性がある）。

   再取得後に矛盾なく再開できるか。
