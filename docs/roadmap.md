## 分かっていること（計画の前提）

- **解けない区間は情報がない区間。** 精密解析で解けない本は、どれも確かな読みが 1 つもない区間が 1〜3 秒ある（見え方の 60〜80% は
  確かな読みゼロ）。解き方の工夫（区間をまたぐ式の #103）では越えられなかった。増やすべきは読める量
- **読めない原因の一番手は録画の圧縮。** 直接読んだ ID の誤りは 0.1〜0.6% とほぼ正しい。読みの誤りの大半は、面の中身は正しいのに
  「正面・上・右」のスロットや格子の向きだけが違うもの（9 マスが一度に外れる）
- **低い画質は圧縮のたびに成否が変わる。** 同じ動画でも圧縮ごとに 1 方式あたり 2〜3 本が「完成」と「つながらない」で入れ替わる。
  比べは bench-2（`-threads 1` で毎回同じに作れる材料。ハッシュは `docs/history.md`）で、判断は開始をずらした 3 通りの圧縮で
- **ピース方式（表の AND 版）は確定の間違いが少ないが、つながる本が少ない。** bench-2 で、今の方式は完成 26・正解と同じ 24・確定の間違い
  13 / 209（まとめた形 / 状態で照らす）・最大 162.7 秒、表の AND 版は 21・21・0 / 71・6.4 秒
- **2 面見えていれば 13 ピース（3 面なら 16 ピース）が分かり、どの面の手も見えているピースを必ず動かす。** 情報はステッカーの枚数では
  なくピースの数で数える。1 ピース 1 枚読めれば位置と向きが決まる
- **ライブと精密解析は目的が違う。** ライブは今までのフレームだけで、3D を見えているキューブと同じにする（手順は当てなくてよい）。
  精密解析は全部のフレームで、正しい手順とタイムを出し、間違いを確定にしない

## 2 本立てで並行して進める

ライブと精密解析は別々のセッションで同時に進めてよい。ぶつからないための決まり:

- 精密解析の作業は、ライブの追跡・表示・開始と停止の判定（`src/app/startDetect.ts`、`timer.ts` の `onFrame`、`engine.ts` の
  `looksSolved`、`controller.liveConfig`・`liveEngineOptions`、ライブの新しい追跡のファイル、`LiveCube3D`・`gyro`）を触らない
- ライブの作業は、精密解析の解き直し（`src/track/pieces/` の解き方・`offline.ts`・`refine.ts`・`timer.ts` の解析まわり）を触らない
- 共通の部品（`decoder.ts`・`observer.ts`・`src/track/pieces/model.ts`・`tables.ts`・置き方の決め方など）は、足すだけにする。変えるときは
  設定で片方だけに効かせ、もう片方の既定を変えない
- 1 つのセッションで 1 つのプロンプト（作業）。PR を作る前に main に合わせ直し、マージのたびに次の作業を合わせ直す
- 測るときは、版を git worktree で固定して結果に版を書く・計測中にコードを触らない・時間は 1 本ずつ別のプロセスで

## 精密解析

| 順 | 作業 | 状態 |
|---|---|---|
| 1 | 録画をキューブの周りだけ切り出す | 進行中（2026-11-21 に開始） |
| 2 | 物差しを整え、今の方式の不具合を直す | 未着手 |
| 3 | ピース方式に面の扱い・物理の決まり・弱い読みを入れる | 未着手 |
| 4 | 既定をピース方式に切り替えるかの判断 | 未着手（1〜3 の後） |
| 5 | 今の方式（`decoder.ts`）の観測のコストをピース単位にする | 未着手（2 の後ならいつでも） |

1. **録画をキューブの周りだけ切り出す**: 画面全体（長辺 1280・5Mbps）ではなく、キューブの周りだけを同じ 5Mbps で録り、マーカー 1 個あたりの
   データ量を増やす。まず手元で効果を測り（画面全体 / 元の解像度から切り出し / 1280 から切り出し × 5・2.5・1.5Mbps × 3 通りの圧縮）、
   小さければ入れない。入れるなら切り出しの位置を残して元の座標に戻す。照明（明るく）とカメラの置き方（D の段が写る低め）を使い方に書く
2. **物差しと今の方式の不具合**:
   - 速報値・一部推定になった理由を記録に残す（`Solve.analysisReason`。解析の時間・録画のビットレート・間引き・切り出しの大きさも）
   - 今の方式が 1.5Mbps で 13 手を確定のまま間違える件（後ろ向きだけの答えの確かめの後も残る）。ピース方式がつながらないと
     この方式に戻るので本体にも効く
   - 今の方式の時間の上限（最大 162.7 秒 → Node で 30〜40 秒、超えたら一部推定か速報値）
   - 打ち消しの組（確定の L' … L）を 5 組、フレームの画像で見て、本当の無駄な動きか読み違いかを決め、確定の間違いの本当の数を出し直す
   - E2E のタイマーの「一部推定」の頻度（20 回）、`bridge.test.ts` の 30ms の制限
3. **ピース方式の強化**: 置き方を前後の確かな置き方からの続きで決めて確かな読みを増やす・物理の決まり（ねじれ・反転・偶奇・同じ
   ステッカーは 1 か所・隣の面と接するマスは同じピース）で読み違いを見つける・弱い読みも ε の重みつきの外してよい式にする
   （区間をまたぐ式の #103 のブランチ `claude/permutation-table-cross-interval-olqbe8` を土台にしてよい）
4. **既定の切り替えの判断**: ピース方式（つながらなければ今の方式に戻る）と今の方式を、28 本・本体の `Refiner`・E2E 10 回で並べる。
   目標は、確定の間違いが今の方式より少ない・正解と同じが今の方式以上・中央 1.5 秒・最大 4 秒以内・一部推定と速報値が増えない
5. **`decoder.ts` をピース単位に**: 同じピースを 2〜3 面で見たら 1 回分、食い違いの重みは実測の ε から。精密解析の設定でだけ有効にし、
   ライブは変えない

## ライブ

| 順 | 作業 | 状態 |
|---|---|---|
| ライブ 1 | 開始と停止を、追跡に頼らない判定にする | 済み（2026-11-21。`src/track/homeView.ts`・`startDetect.ts`・`stopDetect.ts`。docs/history.md の「タイマーの開始と停止を ID で見る」） |
| ライブ 2 | ソルブ中の 3D を、状態の推定として作り直す | 未着手（ライブ 1 の後） |
| ライブ 3 | 精密解析の遅れた結果で、長い見失いを直す | 案のみ（ライブ 2 の後に必要なら） |

**困っていること**（使っていて）: 3D が実物とずれて見える・タイマーが勝手に始まる・**3 面を見せないと止まらない**。

**ライブの設計で決めたこと**

- **場面ごとに目的を分ける**（同じ部品を使い、判定の基準を変える）
  - スクランブル中: 手を 1 つずつ確実に（今の追跡でよい）
  - インスペクション → 開始: 追跡とは別の慎重な判定。タイムは精密解析が決め直すので、開始が少し遅れてよい。早く始まらないことを優先
  - ソルブ中: 3D の見た目を合わせる
  - 完成 → 停止: 追跡に頼らない。早く止まらないことを優先（タイムは精密解析が決める）
- **停止はマーカーの ID で直接見る**: 今は追跡が揃うか、予備として**色**で「2 面以上・各 6 マス以上が 1 色」が 3 フレーム（追跡が確かなら
  さらに 1 秒）。追跡がずれると止まらず、色の予備は 2 面目が揃いにくいので 3 面見せないと止まらなかった。読めたステッカー
  （10 枚前後）が全部「揃ったときの自分の場所」にいる状態が 0.2 秒続いたら止める。ID で見るので PLL の途中（色は揃って見えるが
  場所が入れ替わっている）では止まらない
- **開始は 2 つの証拠が揃ってから**: スクランブルの状態から ID で見て確かに変わった（2 観測以上）かつ層が動いたのをフレームで見た。
  持ち替え（全部の ID が一緒に動く）・作り変え・1 フレームの読み違いでは始めない。E2E で 7.7 秒早く始まった回がある
- **向きを別に追う**: 前後のフレームで同じ ID のマーカーの動きから、回していない 2 層（多数派）のキューブ全体の回転を求め、面の置き方を
  決める（スロットのラベルに頼らない）。センターが 2 つ読めたら決め直す。中層回しの扱いを決める。自信がなければ候補を 2〜3 通り
- **状態の推定は表の AND**: フレームの間は 0〜2 手が多いので、読めたピースの式で表 T[k][x][y] を引いて AND し、合う状態を全部持つ
  （上位何個で切らない）。追跡は 1 フレーム 3ms 以内。ライブの 1 フレームは認識が 30ms 前後で、追跡を軽くしても処理できる枚数は
  ほとんど増えない（得られるのは正確さ）
- **見えていないピースは「分からない」のまま持つ**: 作り変えが見えていない面を推測で埋め、外れて見えるたびにずれるのが長い見失いの元だった。
  3D はカメラと同じ向きなので見えていない面は画面に映らない
- **表示を少し遅らせて正確にする**（遅れて正確になる方を選ぶ）: 0〜300ms で測って選ぶ（0.2 秒で一致 81.5 → 83.6%）。候補の状態がどれも同じ
  手で説明できるときだけ回して見せ、分かれたら静かに塗り替える
- **精密解析で後から直す**（ライブ 3）: 精密解析は実時間に追いつかないので目の前のずれには使えないが、5〜10 秒続く長い見失いを数秒遅れで
  付け直すのには使える。途中結果は前向きだけで不確かなので、確定した部分だけ使う

## 後回しにした案

- **今の方式と答えが同じ手を確定に戻す**: ピース方式の inferred が多いままなら考える（両方が同じ間違いをすることもあるので、測ってから）
- **SAT ソルバーに解かせる**: 式を書くだけで解かせる。ピース方式が詰まったときの別の道
- **認識を GPU で**: 今は認識も追跡も CPU（WASM SIMD + JS、Web Worker）。GPU は 3D の表示、録画の圧縮・復号は専用の回路。二値化は画像全体で
  8ms ほどで、読み戻しの時間を考えると差は小さい。ライブの枚数を増やしたくなったときに縮小・明るさ・二値化をまとめて移す候補
- **マーカーの配置を変える**: 1 個の大きいマーカーは圧縮・ぶれ・遠さに強く指に弱い。印刷し直しが要るので、録画の切り出しまで試して
  足りないときの最後の手段
- **速報値の理由の記録を実機で集める**: 精密解析 2 の後、実機で何回か解いて、どの理由で速報値・一部推定になるかを見る
