## 分かっていること（計画の前提）

- **解けない区間は情報がない区間。** 精密解析で解けない本は、どれも確かな読みが 1 つもない区間が 1〜3 秒ある（見え方の 60〜80% は
  確かな読みゼロ）。解き方の工夫（区間をまたぐ式の #103）では越えられなかった。増やすべきは読める量
- **読めない原因の一番手は録画の圧縮。** 直接読んだ ID の誤りは 0.1〜0.6% とほぼ正しい。読みの誤りの大半は、面の中身は正しいのに
  「正面・上・右」のスロットや格子の向きだけが違うもの（9 マスが一度に外れる）
- **低い画質は圧縮のたびに成否が変わる。** 同じ動画でも圧縮ごとに 1 方式あたり 2〜3 本が「完成」と「つながらない」で入れ替わる。
  比べは bench-2（`-threads 1` で毎回同じに作れる材料。ハッシュは `docs/history.md`）で、判断は開始をずらした 3 通りの圧縮で
- **ピース方式（表の AND 版）は確定の間違いが少ないが、つながる本が少ない。** bench-2 で、今の方式は完成 26・正解と同じ 24・確定の間違い
  13 / 209（まとめた形 / 状態で照らす）・最大 162.7 秒、表の AND 版は 21・21・0 / 71・6.4 秒
- **2 面見えていれば 13 ピース（3 面なら 16 ピース）が分かり、どの面の手も見えているピースを必ず動かす。** 情報はステッカーの枚数では
  なくピースの数で数える。1 ピース 1 枚読めれば位置と向きが決まる
- **ライブと精密解析は目的が違う。** ライブは今までのフレームだけで、3D を見えているキューブと同じにする（手順は当てなくてよい）。
  精密解析は全部のフレームで、正しい手順とタイムを出し、間違いを確定にしない
- **録画の画質で伸ばせる幅は小さいかもしれない。** 読めたマスは元の画質 8.56・5Mbps 8.2、8Mbps でも +0〜0.4、解像度 1280 → 1920 で
  +0〜4%（`docs/history.md`）。切り出しはマーカー 1 個あたりのビットレートを上げることなので、届くのは元の画質まで
- **今の方式は途中で見失うと最後まで戻らない。** 前から状態を積み上げるので、一度ずれるとその後が全部ずれる（実機でも同じ）。ピース方式は
  読みがキューブ固定の座標の式なので黙ってずれ続けないが、前向きと後ろ向きがつながらないと本全体をあきらめて今の方式に戻る
- **ライブの外れはほとんど「違う状態」で、遅れではない。** 表示を遅らせても 0.2 秒で 81.5 → 83.6%、2 秒でも 84.3%。実機では、キューブを
  傾けただけで 3D が一瞬層を回して見せる（面の割り当てが一瞬入れ替わり、追跡がそれを手で説明している）

## 2 本立てで並行して進める

ライブと精密解析は別々のセッションで同時に進めてよい。ぶつからないための決まり:

- 精密解析の作業は、ライブの追跡・表示・開始と停止の判定（`src/app/startDetect.ts`、`timer.ts` の `onFrame`、`engine.ts` の
  `looksSolved`、`controller.liveConfig`・`liveEngineOptions`、ライブの新しい追跡のファイル、`LiveCube3D`・`gyro`）を触らない
- ライブの作業は、精密解析の解き直し（`src/track/pieces/` の解き方・`offline.ts`・`refine.ts`・`timer.ts` の解析まわり）を触らない
- 共通の部品（`decoder.ts`・`observer.ts`・`src/track/pieces/model.ts`・`tables.ts`・置き方の決め方など）は、足すだけにする。変えるときは
  設定で片方だけに効かせ、もう片方の既定を変えない
- 1 つのセッションで 1 つのプロンプト（作業）。PR を作る前に main に合わせ直し、マージのたびに次の作業を合わせ直す
- 測るときは、版を git worktree で固定して結果に版を書く・計測中にコードを触らない・時間は 1 本ずつ別のプロセスで

     - 島 = 確かな読みで続いている見え方のまとまり。島の中は今の表の AND で解き、答えの確かめ（`verifyPath`）も島の中で行う

     - 今の方式に戻すのは、島に分けても確定がほとんど取れなかったときだけ。物差しは「確定にできた手の割合」と確定の間違い

     確かな読みゼロの区間で、手数と使った面を絞る手がかりにする（今は今の方式でしか使っていない）
   - 置き方を前後の確かな置き方からの続きで決めて確かな読みを増やす・物理の決まり（ねじれ・反転・偶奇・同じステッカーは 1 か所・隣の面と
     接するマスは同じピース）で読み違いを見つける・弱い読みも ε の重みつきの外してよい式にする（区間をまたぐ式の #103 のブランチ
     `claude/permutation-table-cross-interval-olqbe8` を土台にしてよい）

   少ない」（2.5Mbps でまとめた形 0 → 3: 画像で見て本当の間違い、状態で照らして原画質 0 → 6・2.5Mbps 8 → 16）と、2026-11-28 に足した

   - **確定の間違い**: 速い区間を半回転にまとめ、持ち替えの所の推定の手で辻褄を合わせる（`IMG_5048` の 2.5Mbps）。層が止まってから回したのを
     フレームで見た回数（`separateMotions` と同じ手がかり）と手の数が合わない区間の手は確定にしない
   - 実機の録画でつながる本が増えること（実機の読める量は 1.5Mbps に近い: 撮り方の案内・ライブ 2.5 の fps の低下の後に測り直す）

**ライブ 1.5**（済み）: 3D で層を回して見せるのは、その手の層が動いたのをフレームで見たとき（`MoveTiming.moved`）だけにした。見ていない手は

**ライブの設計で決めたこと**

- **場面ごとに目的を分ける**（同じ部品を使い、判定の基準を変える）
  - スクランブル中: 手を 1 つずつ確実に（今の追跡でよい）
  - インスペクション → 開始: 追跡とは別の慎重な判定。タイムは精密解析が決め直すので、開始が少し遅れてよい。早く始まらないことを優先
  - ソルブ中: 3D の見た目を合わせる
  - 完成 → 停止: 追跡に頼らない。早く止まらないことを優先（タイムは精密解析が決める）
- **停止はマーカーの ID で直接見る**: 今は追跡が揃うか、予備として**色**で「2 面以上・各 6 マス以上が 1 色」が 3 フレーム（追跡が確かなら
  さらに 1 秒）。追跡がずれると止まらず、色の予備は 2 面目が揃いにくいので 3 面見せないと止まらなかった。読めたステッカー
  （10 枚前後）が全部「揃ったときの自分の場所」にいる状態が 0.2 秒続いたら止める。ID で見るので PLL の途中（色は揃って見えるが
  場所が入れ替わっている）では止まらない
- **開始は 2 つの証拠が揃ってから**: スクランブルの状態から ID で見て確かに変わった（2 観測以上）かつ層が動いたのをフレームで見た。
  持ち替え（全部の ID が一緒に動く）・作り変え・1 フレームの読み違いでは始めない。E2E で 7.7 秒早く始まった回がある
- **向きを別に追う**（済み: `src/track/orient.ts`）: 前後のフレームで同じ面を突き合わせ（スロットのラベルに頼らない）、同じマスに残った
  ステッカー = 回していない層、とする。実物では角を向けて持つと割り当てが 1 つの回転にならない入れ替わり方をするので、回転そのものは
  決めず、動いていないステッカーが十分あれば持ち替えを安くし、短い間で動いていないと分かったステッカーを動かす手にコストを足す。向きの
  候補はデコーダの仮説が持ち、センターが 2 つ読めれば 1 つに決まる。中層回し・両側を同時に回す手では動いていないステッカーが減るだけ。
  35 通りでソルブの前に数えた偽の手 20 → 4・ソルブ中の結びつかない手 595 → 546・3D の一致 71.5 → 72.9%。ソルブ中の残りの偽の手の多くは
  カメラに近い面（D）の速い手の数え違いで、傾けではない（次の表の AND で扱う）
- **状態の推定は表の AND**（済み: `src/track/liveState.ts`。35 通りで数えた手のソルブ中の結びつかない 546 → 379・ソルブ中の 1 フレーム 99% 17 → 1.5ms・
  3ms を超えた 2.5 → 0.5%。3D の一致は同じ（72.8 → 72.9%）、3D で回して見せた本当の手は 47.5 → 42.2%）: フレームの間は 0〜2 手が多いので、読めたピースの式で表 T[k][x][y] を引いて AND し、合う状態を全部持つ
  （上位何個で切らない）。追跡は 1 フレーム 3ms 以内。ライブの 1 フレームは認識が 30ms 前後で、追跡を軽くしても処理できる枚数は
  ほとんど増えない（得られるのは正確さ）。見えない面が続くと候補が膨らんで 3ms を超えうるので、超えたらピースごとに「取り得る位置の
  ビット」だけを持つ近似に落とす（確かに決まったピースだけ 3D に反映する）。中層回し・両側を同時に回す手・持ち替えながらの手では
  「回していない 2 層」自体が動くので、向きの候補を並べて持つのは必須
- **見えていないピースは「分からない」のまま持つ**: 作り変えが見えていない面を推測で埋め、外れて見えるたびにずれるのが長い見失いの元だった。
  3D はカメラと同じ向きなので見えていない面は画面に映らない
- **向きは遅らせず、層の回転だけ待つ**: 表示を遅らせても一致はほとんど上がらない（0.2 秒で 81.5 → 83.6%、2 秒でも 84.3%）うえ、遅れは
  もっさり見える。キューブ全体の向きは遅れなしでカメラに合わせ、層を回すアニメーションだけを 100〜150ms 待って確かめてから速めに回す。
  候補の状態がどれも同じ手で説明できるときだけ回して見せ、分かれたら静かに塗り替える
- **精密解析で後から直す**（ライブ 3）: 精密解析は実時間に追いつかないので目の前のずれには使えないが、5〜10 秒続く長い見失いを数秒遅れで
  付け直すのには使える。途中結果は前向きだけで不確かなので、確定した部分だけ使う

## 後回しにした案

- **調べる道具の穴**（2026-11-27 に追加。実機の比べで分かった）: ライブの記録を捨てた後に通し直せない件は直した（ライブ 2.5: 区切りの始まりを
  落ち着いた時点に進める）。書き出した iPhone の録画を手元で解析し直すとアプリの
  結果と同じにならない（解析の Worker が処理したフレームの時刻か画素のハッシュを `decodeInfo` に残して、どこで分かれるかを見る）
- **今の方式と答えが同じ手を確定に戻す**: ピース方式の inferred が多いままなら考える（両方が同じ間違いをすることもあるので、測ってから）
- **SAT ソルバーに解かせる**: 式を書くだけで解かせる。ピース方式が詰まったときの別の道
- **認識を GPU で**: 今は認識も追跡も CPU（WASM SIMD + JS、Web Worker）。GPU は 3D の表示、録画の圧縮・復号は専用の回路。二値化は画像全体で
  8ms ほどで、読み戻しの時間を考えると差は小さい。ライブの枚数を増やしたくなったときに縮小・明るさ・二値化をまとめて移す候補
- **速報値の理由の記録を実機で集める**: 精密解析 2 の後、実機で何回か解いて、どの理由で速報値・一部推定になるかを見る
- **長い動画から複数のソルブをまとめて取り込む**（2026-11-22 に追加）: カメラアプリで撮った 60・120fps の動画（例: 1 時間で 30 ソルブ）を
  そのまま読み込み、ソルブごとに切り分けて記録に足す。今の動画ファイルの解析（`VideoAnalysis.tsx`）は 1 本 1 ソルブで、スクランブルを先に
  渡す必要がある。要るもの: 「スクランブル → インスペクション → ソルブ → 揃う」の区切りを見つける（ライブ 1 の ID の判定が土台）・前の
  ソルブの終わり（揃った状態）からスクランブルを追って始まりの状態を決める・処理時間（60fps の 1 時間は約 21 万フレーム、今の 1 フレーム
  16ms ほどで PC でも約 1 時間。スクランブル中は粗く・止まったフレームは飛ばす）・数 GB の動画を少しずつ復号する・取り込んだソルブの一覧
  （消す・+2・DNF）。元の動画は録画（5Mbps）より画質がよいので、精密解析 1a の結果がこの機能の見込みにもなる
- **ネイティブアプリ**（2026-11-22 に追加）: iOS のネイティブ（AVFoundation）なら 60fps・120fps（機種によって 4K 120fps）で撮れ、圧縮前の映像を
  精密解析に回せる（今の一番の弱点の録画の圧縮がほぼ消える）。120fps でライブを全フレーム処理するには 1 フレーム約 8ms で、今の認識（30ms
  前後）の数倍速くする必要があるので、録画だけ高 fps にして精密解析で使う形が現実的。まずはネイティブのカメラで高画質・高 fps の動画を
  撮って精密解析に通し、効果を測る
- **CFOP の途中の形（クロス・F2L の完成）を読めない区間の手がかりにする**: 定石の知識に合わせて間違った手を選ぶ危険があるので、ピース方式では
  島に分けた後に必要なら考える
