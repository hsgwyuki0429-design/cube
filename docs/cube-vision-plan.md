## 1. 企画概要

### 1.1 一言で

**「持っているキューブが、そのままスマートキューブになる」**

### 1.2 解決する課題

GAN / MoYu などのスマートキューブは、Bluetoothで1手ごとの回転を送信し、リアルタイムタイマー・手順リプレイ・オンライン対戦を可能にした。しかし：

1. **専用キューブを買わないと使えない**（1〜2万円）。手持ちの愛用キューブでは使えない。
2. **キューブが固定される**。競技者は自分に合ったキューブ（バネ強度・磁力・潤滑）を厳密に選ぶが、スマート機能を使うにはその選択を捨てる必要がある。
3. **バッテリー・ペアリングの手間**、充電切れ、経年劣化。
4. **大会公式キューブでは使えない**（多くの公式戦でスマートキューブは非推奨/不可）。

→ **カメラ1つで同じ体験を提供できれば、市場全体（キューバー人口）がターゲットになる。** スマートキューブ所有者は一部に過ぎない。

### 1.3 コアバリュー

- **ゼロハードウェア**: スマホとスタンドだけ。追加投資ほぼなし
- **どのキューブでも**: 手持ちの本命キューブでオンライン対戦・分析ができる
- **ブラウザ完結**: インストール不要、URLひとつで即体験。拡散性が最大

### 1.4 想定ユーザー

| セグメント | 規模感 | ニーズ |
|---|---|---|
| 中級キューバー（Sub-30〜Sub-20） | 最大ボリューム | 手順分析で伸びたい。スマートキューブは高い |
| 上級・競技勢（Sub-15〜） | コア層 | 本命キューブを変えたくない。詳細統計が欲しい |
| 初心者・興味層 | 流入源 | まず遊びたい。ソルバー・チュートリアルが入口 |
| 配信者・大会運営 | 拡散のハブ | 手順オーバーレイ・観戦機能 |

## 2. 競合と差別化

| 競合 | 形態 | 強み | 弱み（=我々の余地） |
|---|---|---|---|
| GAN Smart Cube + GAN Cube アプリ | HW+アプリ | 完璧なトラッキング精度、ブランド力 | 専用キューブ必須、高価、キューブ選択の自由なし |
| MoYu AI / Giiker | HW+アプリ | 安価な選択肢 | 同上 |
| csTimer | Web計測 | 事実上の業界標準、統計が強い | 手動計測、手順追跡なし |
| ChaoTimer / Twisty Timer | アプリ計測 | 手軽 | 同上 |
| cstimer + スマートキューブ連携 | ハイブリッド | 一部連携可 | やはりHW依存 |
| カメラ式スキャナ（各種ソルバーアプリ） | 静止スキャン | 状態読み取りのみ | **リアルタイム手順追跡をやっているものは実質存在しない** |

### 差別化の核

「カメラでキューブの色を読む」は既存技術（ソルバーアプリで多数）。
**未踏なのは「回転を1手ずつリアルタイムに検出し続ける」部分。** ここが技術的堀（moat）であり、同時に最大リスク（§9）。

## 3. プロダクト設計

### 3.1 画面構成（v1）

```
[ホーム]
 ├─ [ソロタイマー]  ← MVPの主戦場
 │    ├─ カメラプレビュー + 認識オーバーレイ
 │    ├─ スクランブル表示（WCA準拠生成）
 │    ├─ スクランブル一致確認（カメラで検証）
 │    ├─ 計測中HUD（経過時間 / 手数 / TPS / 検出状態）
 │    └─ [リザルト画面]
 │         ├─ タイム・手数・TPS・分割区間（Cross/F2L/OLL/PLL）
 │         ├─ 3D手順リプレイ（速度調整・巻き戻し）
 │         └─ 改善ポイント（無駄手検出・停止時間ヒートマップ）
 ├─ [統計・分析]  ← ローカルDBのみでも成立
 ├─ [キャリブレーション]  ← カラースキーム登録
 ├─ [対戦]（フェーズ2）
 └─ [設定]
```

### 3.2 コアループ

```
スクランブル提示
  → カメラでスクランブル適用状態を検証（一致するまで待機）
  → 手を離す/インスペクション開始
  → 15秒インスペクション（WCA準拠、任意）
  → 最初の回転検出 = 計測開始（自動）
  → 全手順を逐次記録
  → 完成状態検出 = 計測終了（自動）
  → リザルト + 分析
```

**重要**: タイマーの開始/終了がキューブ主導で自動なのが、スマートキューブ体験の本質。ここが手動タップに落ちると「ただのスキャナ付きタイマー」になり、価値が半減する。

### 3.3 計測の妥当性ポリシー

- 内部状態は**キューブ状態のシミュレーション**が真実（cubejs的な状態遷移モデル）
- カメラは「どの回転が起きたか」の観測にすぎない
- **矛盾検出**: 観測色と内部状態が乖離したら即座に「ロスト」表示。ごまかさない
- ロスト時は「再スキャンして復帰」または「そのソルブを無効化」をユーザーが選択
- **信頼度スコア**を各ソルブに記録。低信頼ソルブはランキングから除外（フェーズ2の不正対策の土台にもなる）

## 4. 技術設計：認識エンジン（本書の中核）

### 4.1 3つのアプローチ比較

#### A. 古典的CV中心（OpenCV.js）

- 輪郭検出 → 四角形抽出 → 3x3グリッド射影 → 色クラスタリング
- **Pros**: 学習データ不要、モデル配信なし（軽量）、デバッグが目で見える、CPUのみで動く
- **Cons**: 照明・影・反射に極端に弱い。ステッカーレスキューブの艶反射で色が飛ぶ。手が面を隠すと即崩壊。パラメータ調整が沼

#### B. 機械学習中心（ONNX Runtime Web / TFJS + WebGPU）

- 学習済みモデルで「キューブ検出 → 面セグメンテーション → 姿勢推定 → 回転分類」
- **Pros**: 照明・遮蔽に頑健。多様なキューブに汎化しやすい。精度の天井が高い
- **Cons**: 学習データ収集・アノテーションが重い（数千〜数万フレーム）。モデルサイズがPWAの初回ロードを圧迫。WebGPU非対応端末でのフォールバック設計が必要

#### C. ハイブリッド（推奨）★

**役割分担**:

```
[段階1] キューブ検出・姿勢推定    → 軽量ML（物体検出 or キーポイント回帰）
[段階2] 面の射影補正・色サンプリング → 古典CV（ホモグラフィ変換）
[段階3] 色分類                     → キャリブレーション済み最近傍（古典）＋不確実時のみML
[段階4] 回転検出                   → 状態機械 + オプティカルフロー + ML補助
```

**推奨理由**:
- 姿勢推定だけをMLに任せれば、学習データは「キューブの向き」のアノテーションで済む（色ラベル付けより桁違いに軽い）
- 色分類は**ユーザーごとのキャリブレーション**が最強の解。汎用モデルより、そのキューブのその照明下の6色を実測した方が精度が出る。「どんなカラースキームでも」の要件を最も素直に満たす
- 段階1が失敗しても段階2〜4は落ちない層構造にできる

### 4.2 カラースキーム対応（要件の核心の1つ）

**アプローチ: 初回キャリブレーション・ウィザード**

```
1. 「白い面をカメラに向けてください」…ではなく
   「面1をカメラに向けて → 回して → 面2 …」を6回
2. 各面の中央キュービーの色をHSV/Lab空間でサンプリング（複数フレーム平均）
3. 6色の代表ベクトルを保存 = そのキューブのカラープロファイル
4. 色分類は「6つの代表ベクトルへの最近傍」でOK
   → パステル/ステッカーレス/変則配色すべてこれで吸収できる
5. 照明が変わったら再キャリブレーション（または実行中の適応更新）
```

**さらに堅牢化**:
- Lab色空間 + 明度正規化で照明強度変化に耐性
- 6色間の**最小距離**をチェックし、判別困難な配色（似た2色）は警告
- 実行中の**オンライン適応**: 高信頼フレームで代表ベクトルを緩やかに更新（EMA）

**プロファイル保存**: 複数キューブを登録・切替可能に（「本命」「練習用」など）

### 4.3 回転検出（最難関）

**基本方針: 状態推定は「フレーム差分」ではなく「状態照合」で行う**

```
内部状態 S（54ステッカーの色配置）を保持
毎フレーム:
  1. 見えている面の色を読む（1〜3面が見える）
  2. 現在の S から予測される見え方と照合 → 一致なら「無回転」
  3. 不一致なら、S から1手（U/U'/U2/D/.../B2 の18通り）適用した候補状態
     それぞれの予測見え方と照合
  4. 最も一致する候補を採用 → S を更新、手順ログに追加
  5. どれも閾値以下 → 複数手同時 or ロスト判定
```

**この設計の利点**:
- 「回転を映像から検出する」という難問を「18通りの候補から選ぶ」という**分類問題に落とせる**
- 誤り訂正が効く（ありえない状態遷移を排除できる）
- キューブ全体の持ち替え（回転 x/y/z）も候補に加えれば同様に扱える

**課題と対策**:

| 課題 | 対策 |
|---|---|
| 高速ソルブでは1手が2〜3フレームで完了（TPS 8〜10） | **高フレームレート必須**。60fps以上を確保。理想は120fps撮影 |
| モーションブラー | 露光時間を短く（`ImageCapture` の制約指定 / 明るい環境推奨） |
| 手による遮蔽（常に一部が隠れる） | 見えているステッカーのみで**部分照合**。スコアを可視面積で正規化 |
| 複数手が1フレーム間に起きる | 2手先まで候補展開（18×18=324通り。刈り込み必須） |
| 持ち替え（キューブ回転）と面回転の混同 | 別カテゴリとして候補に含め、直後の整合性で判定 |

**フレームレート戦略**:
- `getUserMedia` で 60/120fps を要求（`frameRate: {ideal: 120}`）
- 処理が追いつかない場合、**認識処理は間引くが記録は間引かない**設計に
- WebCodecs / OffscreenCanvas + Worker で描画スレッドから分離必須

### 4.4 カメラ配置とスコープの割り切り

**固定スタンド前提の恩恵は極めて大きい**:
- カメラ姿勢が固定 → 背景差分が有効、キューブ位置の探索範囲を絞れる
- キャリブレーションが1度で済む
- 照明条件が安定

**セットアップ・ガイド機能**:
- 画面に推奨配置のシルエットを表示し、「良い/悪い」をリアルタイム判定
- 明るさ・キューブサイズ・傾きをスコア化し、開始前にグリーンにさせる
- **これは機能というより歩留まり対策。ここを手抜くとサポート地獄になる**

### 4.5 見えない面の問題（設計上の重要判断）

固定カメラでは**最大3面（27ステッカー）しか見えない**。裏側は原理的に不可視。

→ だからこそ**§4.3の状態照合方式が必然**。裏側は「スクランブルから決定論的に計算した内部状態」で持ち、カメラは前面の整合性チェックにのみ使う。

**帰結**: スクランブル状態の確定が生命線。
- スクランブルはアプリが生成 → ユーザーが適用 → **カメラで検証**（前面3面が一致するか）
- 完全検証は不可能なので、「3面一致 + ユーザー確認」で開始
- 途中でロストした場合の復帰は、6面スキャンモード（ユーザーが意図的に全面を見せる）

### 4.6 技術スタック（v1）

```
フロント: TypeScript + Vite + PWA (Workbox)
UI: React（または軽量に Preact）
3D: three.js（キューブリプレイ表示、既存の知見を流用可能）
CV: OpenCV.js（wasm）＋ 自前の軽量処理
ML: ONNX Runtime Web（WebGPU backend / WASM fallback）
状態モデル: 自前実装（cubejs / min2phase の考え方を参照）
ソルバー: min2phase の WASM 移植（分析用の最適解比較）
ストレージ: IndexedDB（Dexie）
計測: Web Worker + OffscreenCanvas + WebCodecs
```

## 5. データモデル（ローカルMVP）

```ts
CubeProfile {
  id, name,
  colorVectors: Lab[6],       // キャリブレーション結果
  scheme: 'standard' | 'custom',
  createdAt, lastUsedAt
}

Session {
  id, name, cubeProfileId, createdAt
}

Solve {
  id, sessionId,
  scramble: string,
  startedAt, timeMs,
  penalty: 'none' | '+2' | 'DNF',
  moves: Move[],              // 手順ログ
  confidence: number,         // 0-1 認識信頼度
  recognitionMode: 'tracked' | 'timerOnly',
  phases: { cross, f2l, oll, pll }  // 自動区間分割
}

Move {
  notation: string,           // "R", "U'", "F2", "y" ...
  tMs: number,                // ソルブ開始からの経過
  confidence: number
}
```

**分析で出せるもの（手順ログがあるからこそ）**:
- TPS（Turns Per Second）と区間別TPS
- **思考停止時間**のヒートマップ（どこで止まっているか）
- 無駄手の検出（最適解との差分）
- F2Lペア別の得手不得手
- OLL/PLL別の実行時間統計・認識時間 vs 実行時間の分離

→ **ここがcsTimerに対する決定的な差**。単なる代替ではなく上位互換になる。

## 8. 実装上の重要な注意点（AIプロンプト化時のメモ）

1. **認識処理はメインスレッドに置かない**。Worker + OffscreenCanvas を最初から。後から分離するのは地獄
2. **内部状態モデルは認識と完全に分離**。純粋なキューブ状態機械を単体でテスト可能にする（ユニットテスト必須）
3. **記録用の生映像バッファを常に保持**。認識が失敗しても、後から映像を再解析できるようにしておくと開発速度が段違い（開発モードのみ）
4. **デバッグ用オーバーレイを最初に作る**。検出した面・色・候補スコアを画面に描く。これなしにチューニングは不可能
5. **テスト用の録画データセットを早期に作る**。自分のソルブを20本録っておけば、以後の改善が定量評価できる
6. **「認識できない」を正直に出す**。無理に推測して間違った手順を記録するのが最悪のUX

## 9. リスクと対策

| リスク | 深刻度 | 対策 |
|---|---|---|
| **高速ソルブで追跡が破綻する** | 致命的 | フェーズ0で検証。ダメなら「Sub-20層向け」にターゲットを絞る、または事後解析モードへ退避 |
| ブラウザのカメラAPIが60fps出ない端末が多い | 高 | 端末別ベンチを取り、非対応端末は「タイマーのみモード」に自動フォールバック |
| モデルサイズでPWA初回ロードが重い | 中 | モデルは遅延ロード + キャッシュ。初回はタイマーのみで即使える設計 |
| 照明環境の個体差 | 中 | キャリブレーション + セットアップガイドで能動的に環境を作らせる |
| iOS Safari の制約（WebGPU、カメラ制約） | 中 | 早期に実機検証。iOSでの動作可否がPWA戦略の分水嶺 |
| 不正（オンライン対戦） | 中（フェーズ2） | 信頼度スコア、映像ハッシュ、異常TPS検出 |

### 撤退・縮退プラン

フェーズ0で高速追跡が成立しなかった場合の**段階的縮退**:

1. **事後解析モード**: リアルタイムは諦め、録画を解析して手順を出す（価値は残る）
2. **ハイブリッド計測**: 開始/終了だけカメラ自動検出、手順追跡はオプション
3. **スキャン+タイマー**: 最低限、csTimer + 自動計測。これでも「スクランブル適用ミスの検出」という独自価値は残る

**この階段があるので、プロジェクト全体が全損することはない。** ここが企画として健全な点。
